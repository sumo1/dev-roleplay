# 00 — 双 SSOT 与三个时间方向

> 这是整套 dev-roleplay-harness 的**前提哲学**。看懂这一篇再看 01-06 的具体协议，否则会把这套体系当成"七个干活的角色"来用。

## 核心主张

**代码和文档都是一等公民。**

- 同一个 repo
- 同一套版本控制
- 同一套 review 纪律
- 同一套腐坏惩罚

它们是项目的**两个 SSOT**——少一个，工程就不完整。

| SSOT | 表达什么 | 为什么不可替代 |
|------|---------|--------------|
| **代码** | 行为真相——系统实际怎么跑 | 但它表达不了"为什么不这么做"、"哪条路被否决过"、"这条路径背后的业务约束" |
| **文档** | 业务知识真相——业务为什么这样、边界在哪、什么被否决过 | 业务意图常常活在**负空间**里——代码只能表达正空间，"曾经选择不这么做"的判断只有文档能保住 |

两者必须**始终一致**。任何一边落后于另一边，那一边就失去了 SSOT 资格——它退化成了装饰。

## 文档为什么必须在 git 里

很多团队把代码放 GitHub，把文档放 Confluence / Notion / 飞书。结果是：

- 文档**不会被 review**——没人在 PR 里看它
- 文档**不会被 diff**——改了什么没人知道
- 文档**不会被回溯**——三个月前的版本无从找回
- 文档和代码**脱节越来越远**——最终没人信文档

文档进 git 不是工程偏好，是**让文档承担 SSOT 责任**的最小条件。如果文档腐坏不会触发 review、不会进 commit history、不会被 doc-refresher 这种角色机器化盯防，它就**不可能**和代码保持同等鲜度。

## 业务意图活在负空间里

代码能告诉你"系统现在做什么"。它告诉不了你：

- 我们曾经想过 A、B、C 方案，**为什么最终不做 A**
- 这个字段为什么是 `snake_case` 而不是 `camelCase`
- 这条路径上为什么不抛异常而是静默降级
- 这个抽象层为什么不存在——之前想过加，被否决了

这些是**负空间**——曾经存在过的可能性，被现在的实现压缩掉了。但下一个改这段代码的人**需要知道**这些被否决的方案，否则他会**重新造一遍"为什么不做 A"的论证**——而且很可能得出错的结论，因为他不知道当年是哪个具体场景把 A 否掉的。

代码无法保留负空间，文档可以。这是文档作为 SSOT 不可替代的根本原因。

## 七个角色服务三个时间方向

整套 agents 不是七个工种的横向流水线，而是**知识在时间轴上的三段流动**：

```
   过去                 现在                    未来
─────────────────────────────────────────────────────
 历史沉淀  ───→   当前任务的拆解 + 执行  ───→  沉淀回去

knowledge/        task-designer                dreamer
engineering/      coder + evaluator              ↓
   ↑              code-reviewer            knowledge/
   │              doc-refresher  ←─保鲜    engineering/
   │                  ↓                         ↑
   └────────  下一次任务从新鲜起点出发  ─────────┘
```

### 过去 → 现在：让历史沉淀真正被用上

- **task-designer**：开工前必读 `engineering/` 规范、`knowledge/` 跨任务知识、最近的 `task/` 决策——不让"已经踩过的坑"再被踩一次

这一段成立的前提是：**过去的沉淀必须是新鲜的**。如果上一轮没有 doc-refresher 把腐坏文档标出来，task-designer 读到的"现状"已经是过期事实——后面整条链都从一开始就漂移。

### 现在：让当前任务真正按已沉淀的约束落地

- **coder**：按双契约施工，复用既有模式、不破坏冻结边界
- **evaluator**：独立复跑，不让漂移产出混过去
- **code-reviewer**：独立看 diff，按工程规范 + 任务专项规则审查

三个独立视角分别拦截不同方向的偏差。详见 [01 — 角色即剧班](./01-roles-as-theater.md)。

### 现在 → 未来：让当前任务产生的知识不流失

- **doc-refresher** = 当下的**保鲜哨兵**——任何代码变更后，把可能腐坏的 SSOT 文档标出来，让调用方决定怎么修。它存在的意义是保证**下一次任务的起点是新鲜的**
- **dreamer** = 业务知识的**酿造师**——把当前任务过程中蒸馏出的判断、被否决的方案、踩坑原因，从 task memory 上浮回 `knowledge/` 和 `engineering/`，让**下一个任务能站在它肩上**

`git-push` 是流水线管家，串起七环；它本身不在三段流动里，是流程闸口。

## 没有这两台引擎会怎么样

把 doc-refresher 和 dreamer 删掉，保留剩下五个角色，会发生什么：

### 没有 doc-refresher

- 文档随每次代码变更默默腐烂
- 三个月后下一个任务起步时，读到的"当前现状"已经不是当前现状
- task-designer 基于过期文档拆任务，coder 基于过期约束施工
- 整条链从一开始就漂移，但**没人发现**——因为漂移的源头在过去

### 没有 dreamer

- 当前任务过程中所有判断（被否决的 A 方案、踩过的 X 坑、为什么选 B 而不是 C）随任务结束而蒸发
- 下次任务遇到相似选择时，要么从零开始论证，要么直接踩同一个坑
- task memory 越积越多但没人提炼——最终淹没在噪音里，没人翻

### 两个一起被砍

业务知识就成了**流水**——每次任务交付完就流走，知识库永远不增长。

整套 agents 退化成"几个干活的角色"——质量靠运气，沉淀靠人记。**LLM 协作的真正杠杆——把一次性对话沉淀为可复用资产——失去了**。

## 两台引擎是 dev-roleplay-harness 的真正杠杆

剧班分工（独立视角）解决的是**"自洽但漂移"**问题——让一次任务做得对。
双 SSOT + 两台引擎解决的是**"一次任务到下次任务之间的知识流失"**问题——让每次任务做得**比上次更好**。

前者是单次质量，后者是**复利（compound）**——每一次改进让下一次改进更容易。

> **Each improvement makes future improvements easier.**

这条标语是整套体系真正的杠杆所在。剧班分工只保证了"这一次做对"，而 compound 才让一支团队（或一个 agent 团）随时间持续变强。

具体怎么 compound：

- **doc-refresher** 让下一次任务读到的"现状描述"是新鲜的——不在腐坏文档上重新论证已经决定过的事
- **dreamer** 让下一次任务直接复用上一次蒸馏出的判断——不重新踩同一个坑
- 两者共同把"业务知识"作为**项目级 SSOT 资产**沉淀下来，而不是停留在某次会话的上下文里

正是这两台引擎，让整个 agents 体系成为一个**自我演进的知识系统**——一台保鲜（防止过去→现在腐坏）、一台沉淀（保障现在→未来畅通）。

## 给 fork 者的提示

你 fork 这套骨架时，**先确认你愿不愿意接受双 SSOT 哲学**：

- 愿意把文档放在 repo 里、和代码一起 review、一起腐坏惩罚 → 这套体系对你有意义
- 不愿意，文档继续放外部工具里 → 这套体系会很快退化成"七个干活的 agent"，doc-refresher 和 dreamer 会变成笑话——它们没有可上浮的家、没有可保鲜的目标

哲学决定上限。把双 SSOT 当真，剩下六篇 doctrine 才有意义。
