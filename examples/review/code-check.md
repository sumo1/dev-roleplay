# 工程审查标准（示例）

> 工程维度的持续审查规则，不绑定任何具体任务。
> 适用于本仓库所有代码和文档改动。
>
> **任务专项审查**见 `task/{id}/task-reviewer/code-review.md`，由 code-reviewer 组合调用。

---

## 1. 审查者角色

站在**独立视角**审查每一轮改动：

1. 改动是否符合工程规范（[`engineering/conventions.md`](../engineering/conventions.md)）
2. 是否引入了不必要的设计负担
3. 是否破坏了已有的模块边界和 API 契约
4. 是否存在会随规模放大的风险

注意 review 标准和 engineering 规范是两个独立 SSOT：

- `engineering/` 告诉 coder **怎么写**
- `review/` 告诉 reviewer **怎么审**

两者重叠但不重合——审查标准里有些项是 coder 自己看不见的（比如"会不会随规模放大"、"和已有契约的隐式冲突"），需要独立视角。

---

## 2. 审查维度（按优先级）

### 2.1 风险分级

| 等级 | 标准 | 行动 |
|------|------|------|
| **高** | 数据一致性、对外契约破坏、安全漏洞、不可逆破坏 | 阻塞提交 |
| **中** | 错误处理不完整、超时/重试/鉴权模糊、与契约不一致、职责混淆 | 强烈建议先修 |
| **低** | 命名、注释、风格、轻微文件组织不一致 | 指出即可 |

风险分级是审查的**第一动作**——所有发现先归一个等级，再讨论怎么修。

### 2.2 职责边界

按项目分层（HTTP / service / repository / mapper 等）逐层检查：

- 入口层：只做参数校验 → 调用 service → 返回 DTO
- 业务层：承担业务规则，不透传数据访问
- 数据层：只做读写，不偷拼 API 响应、不做权限判断
- 字段映射：API 字段可见性的唯一事实来源

**红线**：任何"图方便"打穿分层的写法（route 直接调 repository、service 拼 HTTP envelope 等）都是高风险。

### 2.3 领域模型

- 是否在正确的领域范围内（不把别的域的概念拖进来）
- DTO 是否区分公开 / 内部可见性
- 是否引入了不该暴露的内部字段

### 2.4 语言/框架工程实践

按项目实际技术栈展开。常见检查项：

- 类型安全：避免随意类型断言，优先 schema-first
- 显式 mapper：不在 handler 里临时 mutate 对象
- 禁止 God 类、禁止魔法字符串、禁止预创建空壳模块
- import / dependency 顺序按项目约定

### 2.5 数据迁移与 schema 变更

- 迁移文件结构正确（Up/Down 对称、可逆）
- DDL 变更是否有锁表风险（大表 ALTER、带默认值的 NOT NULL 列）
- 是否存在数据丢失风险（DROP COLUMN、类型收窄）
- 是否在单个 migration 中混合 DDL 和大量 DML

## 3. 固定 Checklist

### 边界

- [ ] 无越域概念引入？
- [ ] 公开 / 内部 DTO 分离？
- [ ] 字段可见性收敛在 mapper？

### 分层

- [ ] 入口层只做校验/调用/返回？
- [ ] 业务层承担业务规则？
- [ ] 数据层只做数据访问？
- [ ] 无 God 类、无打穿分层？

### 错误处理

- [ ] 错误响应格式与项目约定一致？
- [ ] 业务预期错误 → warn，真实错误 → error？
- [ ] 5xx 不泄漏内部异常栈？

### 工程实践

- [ ] 类型安全无逃逸？
- [ ] request/response 有明确类型来源？
- [ ] 新增模块位置合适？
- [ ] 无空壳模块？

### Migration（如适用）

- [ ] Up/Down 对称？
- [ ] 无锁表风险？
- [ ] Schema 与代码已同步？

### 任务专项扩展

任务期间（迁移期 / 重构期 / 契约冻结期）会有额外 checklist 项，由 task-designer 写在 `task/{id}/task-reviewer/code-review.md`，code-reviewer 在工程标准之外**追加**应用。

---

## 4. 输出格式

```text
【核心判断】
✅ 值得继续 / ⚠️ 需要先修正 / ❌ 存在严重工程问题

【风险等级】
- 高风险：
- 中风险：
- 低风险：

【审查发现】
1. [严重级别] [文件/模块] [问题]
2. ...

【边界与分层】
- 职责边界：
- 目录结构：
- 任务专项：（无匹配任务时写 N/A）

【建议】
1. 先修什么
2. 后修什么
3. 哪些不用过度设计
```

## 5. 这份文件和其他 SSOT 的关系

| 文件 | 它是什么 | 由谁维护 |
|------|---------|---------|
| `engineering/conventions.md` | 编码 / 命名 / 错误 / 日志规范——告诉 coder 怎么写 | 工程规范维护者 |
| `engineering/tracing.md` | 工程规范的特定主题（如可观测性）——按需拆分 | 同上 |
| **本文（review/code-check.md）** | **审查标准——告诉 reviewer 怎么审** | reviewer 维护者 |
| `task/{id}/task-reviewer/code-review.md` | 任务专项规则——任务期间的额外审查项 | task-designer 创建，任务结束归档 |
| `knowledge/principles/*.md` | 跨任务通用工程原则——dreamer 上浮的判断准则 | dreamer 提案，调用方批准 |

review 和 engineering 是两个**互相支撑**的 SSOT。如果发现某条规则同时出现在两份文档里——选一边作为权威，另一边引用过去；不允许两份都"权威化"，否则更新时必然漂移。
