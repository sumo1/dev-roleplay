# 03 — 双契约

## 核心主张

每个独立子任务的 plan 文件里，必须同时包含**施工契约**（给 coder）和**验收契约**（给 evaluator）。

两段契约在**同一个文件**里、**指向同一份产出**、**由同一个 task-designer 写**。

这是整个框架里分量最重的一条协议。

## 为什么要双契约

常见做法是：

- 需求写在一个文档里
- 实现规范写在另一个文档里
- 测试要求写在第三个文档里
- 验收标准——通常没有独立文档，散落在代码 review 和 QA 的脑子里

这种散落有三个问题：

1. **施工者和验收者对不上**。coder 觉得"实现到 X 就够了"，evaluator 觉得"必须覆盖 Y"，两人吵架时没人知道谁错。
2. **验收标准迟到**。工程师写完代码，QA 才开始想"我应该怎么验"，这时候已经晚了——很多该在设计时就写清楚的边界条件没考虑。
3. **Agent 协作下放大**。没有明确契约时，人类至少还能靠同事情谊磨合；Agent 则会把每一处模糊都解释成对自己最有利的那种。

**双契约**把这三个问题一次解决：

- 施工前就写清楚要做什么、不做什么
- 同一份文件里写清楚怎么判定做到了
- 两段互相对应，每条施工产出必须有对应的验收条目

## 双契约的形状

在 `docs/task/{task-id}/plan/{step}.md` 里：

```
## 施工契约（给 coder）

### 范围
- 可改文件：...
- 不可改文件：...

### 产出清单
- {具体符号：函数、端点、schema}

### 约束
- {已冻结的边界：响应结构、错误码}

### 复用的现有模式
- {指向同模块已有实现}

## 验收契约（给 evaluator）

### 代码结构验证
- [ ] 文件 X 中新增函数 Y，签名 Z

### 命令验收
| 命令 | 通过标准 |
|------|---------|
| {测试命令} | {可机器判定的通过条件} |

### 数据 / 字段验收
- [ ] 接口响应包含字段 X，类型 Y

### 负面用例
- [ ] 请求缺 X → 返回预期错误码
```

两段不是对仗排比，是**配对**：

| 施工契约声明 | 验收契约对应条目 |
|-------------|----------------|
| "新增 `POST /items` 端点" | "端点 `POST /items` 已在路由注册中出现" |
| "响应保留 `snake_case`" | "接口响应字段命名为 `snake_case`" |
| "不改已有 `ErrorCode.X`" | "错误码 `ErrorCode.X` 未被修改" |

每条施工产出**必须有对应的验收条目**，每条验收条目**必须能追回到施工产出**。

## 写不出验收契约 = 施工契约不合格

这是双契约最重要的一条副作用：**它强迫 task-designer 把事情想清楚**。

如果 task-designer 写完施工契约，写验收契约时发现：

- 有一条施工要求，怎么也想不出可机器判定的验收条目

那通常不是验收能力不够——是**施工契约本身描述得不够硬**。

常见的软描述与对应的硬化：

| 软描述 | 硬化 |
|--------|------|
| "提高性能" | "接口 P95 延迟 ≤ 200ms" |
| "代码要整洁" | "符合项目 lint 规则 0 报错" |
| "保证安全" | "用户输入字段经过 {清洗函数}" |
| "兼容旧接口" | "接口 URL、响应 schema、错误码均未变更" |

写不出验收条目的施工要求，coder 也做不准。所以**task-designer 的自检规则**是：

> 写完验收契约，回看施工契约。如果发现验收契约里缺了东西，原因不是验收想漏了，是施工契约写虚了——回去硬化它。

## 双契约与"可并行"

当任务被拆成多个可并行的子任务时，双契约的价值翻倍。

并行 coder 可能在**不同的会话里**同时施工。如果契约不清，两个 coder 会：

- 动到同一个文件
- 对同一个"约束"有不同解读
- 交付的粒度不一致，后续整合困难

双契约提供的隔离是：

- **文件范围互斥**——施工契约的"可改文件"清单在子任务之间不重叠
- **约束显式**——每个子任务的"约束"都写在自己的契约里，不依赖外部"默认规则"
- **验收独立**——每个子任务的验收条目只针对自己的产出，不要求"跨子任务整合后才能验证"

只要有一条做不到，这组子任务就**不该标为并行**。task-designer 宁可拆得粗一点串行跑，也不要拆得细但互相缠绕。

## 双契约与"可重现"

另一个副作用：同一个 plan 文件可以让**后续 agent 重现原始意图**。

场景：过了 3 个月，某个 bug 和这个 plan 有关，需要回看。

- 只有施工契约 → 知道当时做了什么
- 只有验收契约 → 知道当时怎么验的
- 两者都有 → 知道当时的**完整意图**：想做什么、怎么算做完了

这是文档给未来人的礼物。Agent 时代同样适用——三个月后的那个 agent 也能读懂。

## Dual contract ≠ BDD，≠ test-first

双契约看起来像 BDD（Behavior-Driven Development）或 test-first，但不是。

- **BDD / test-first** 的验证主要在"行为测试"层
- **双契约** 的验证覆盖范围更广：代码结构、命令、数据字段、负面用例、契约边界

另一个差异：

- BDD / test-first 的测试**在施工之后写**（由施工者写）
- 双契约的验收契约**在施工之前写**（由规划者写）

让规划者写验收标准是关键。如果让施工者写，施工者会不自觉地把"我能做到"的东西当成"应该做到"的标准——回到了单 agent 的视角污染问题。

## 双契约不保证完美

诚实地说：双契约**只拦"契约内"的偏差**。

它不拦：

- 契约本身是错的（task-designer 误解了需求）
- 契约遗漏了某个重要维度（没想到某种极端情况）
- 契约写得过死（把创造性空间锁死了）

这些是 **code-reviewer** 和 **人类 reviewer** 的活。双契约把 80% 的机械性验证自动化，剩下 20% 留给更高层的判断。

## 对使用者的操作建议

- **不在 plan 文件外另开验收文档**。验收契约必须在 plan 文件里，就在施工契约旁边。分开会产生漂移。
- **先写施工契约，再写验收契约**。写验收时想不通的地方，倒回去改施工契约。
- **每条验收条目都要可复跑 / 可机读**。"确保代码正确"、"符合最佳实践"这种条目一律打回重写。
- **契约不够就不开工**。宁可让 task-designer 再磨一轮，也不让 coder 带着模糊契约开工。
