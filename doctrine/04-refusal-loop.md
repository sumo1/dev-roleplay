# 04 — 打回循环

## 核心主张

验收者（evaluator）不认施工者（coder）的自报——必须**独立复跑**所有可执行的验收命令。

当同一条契约项被连续打回多轮仍未达标时，**自动升级给调用方**，不让两个 agent 陷入死循环。

## 为什么验收者必须复跑

Agent 协作里最容易发生的失败模式是：

> coder：我跑了测试，全部通过。
>
> evaluator（没跑测试，只读报告）：确认通过。

这条链有三个漏洞：

1. **coder 可能撒谎**——不是有意说谎，而是 LLM 在长上下文里会把"我刚刚跑过"这种事情记混。它可能跑了一半就被错误中断，然后在报告里默认填"通过"。
2. **coder 可能跑错命令**——执行的命令和契约声明的命令不是同一条，但自报"已运行测试"时不会显式列出到底跑的是什么。
3. **coder 可能把失败解释成非失败**——"这个错是既有的，不算本次引入"——这个判断如果 evaluator 不亲自看一眼，就被 coder 的解释垄断了。

让 evaluator 复跑就是在堵这三个漏洞。

## 复跑的硬规则

evaluator 被要求：

- 契约里声明的**每一条**可执行命令都必须亲自跑一次
- 以**复跑结果**为准，与 coder 报告不一致时记录为差异
- 只有**依赖外部环境**（线上服务、第三方 API 等）不便复跑的命令，才接受 coder 的日志 / 截图作为证据——但证据链必须能对上契约

**禁止**凭 coder 的报告判定通过。即使 coder 的报告写得再详细，只要是可复跑的命令，evaluator 不跑就没有判定权。

## 为什么"独立复跑"不能省

有人会说：跑一次已经很贵了，跑两次浪费资源。

这是把"验收"和"测试"混为一谈了。

- **测试**的作用是验证代码行为符合预期——跑一次就够
- **验收**的作用是提供**独立视角**，确认代码确实被验证过——必须由另一个视角重来一次

前者是工程问题，后者是治理问题。治理不能靠"相信被治理者"，必须靠独立核查。

## 失败循环的风险

双契约 + 复跑，解决了"验收被污染"的问题，但引入了新问题：**死循环**。

场景：

1. evaluator 打回 coder，coder 修一轮，再提交
2. evaluator 复跑，还是不过，再打回
3. coder 又修一轮，还是不过
4. ...第 5 轮、第 8 轮、第 20 轮

两个 agent 可能陷入一种**越修越乱**的状态。原因包括：

- coder 不理解 evaluator 的失败描述
- coder 每轮修复引入新问题
- 契约本身歧义，两个 agent 对"达标"的理解不一致
- 环境问题（不是代码的问题，是依赖 / 配置的问题）

## 3 轮升级规则

打回循环的止损机制是：

> 同一条契约项**连续 3 轮**打回仍未达标时，evaluator 判定为 🛑 **调用方裁决**，停止继续循环。

3 这个数字不是神圣的，但它背后的逻辑是：

- 第 1 轮打回：正常的修订
- 第 2 轮还不过：可能是 coder 没理解——再给一次机会
- 第 3 轮还不过：这不是修订问题，是**结构问题**——必须升级

结构问题的常见形态：

- **契约有漏洞**——需要 task-designer 补契约
- **验收标准过严**——需要人类判断是否调整
- **环境问题**——需要人类介入
- **任务拆分错误**——需要重新规划

这些都不是 coder 和 evaluator 能在"再修一轮"里解决的。继续循环只是浪费算力和污染上下文。

## 计数维护在哪里

"连续 3 轮"需要有人数。这个计数**不在 coder 那里，也不在 evaluator 那里**——两边的上下文都不是稳定的持久状态。

计数在**调用方**（通常是主会话 / 调度者）：

- 调用方在 spawn evaluator 时，传入"本轮是第 N 轮"
- evaluator 判定结果里如果是"打回"，调用方把 N+1 记下来
- 到 N=3 时，调用方直接升级为人类裁决，不再 spawn coder

这个设计把**状态**留在调度层，让角色本身保持无状态。

## 争议不是打回

要区分**"打回"**和**"争议"**：

- **打回**：evaluator 判定某条契约项未达标。coder 的任务是修它。
- **争议**：coder 不同意 evaluator 的判定（认为契约本身有歧义，或认为 evaluator 误解了契约）。

打回走 3 轮升级规则。**争议直接上报调用方**，不走循环。

coder 的硬规则：

> 若对 evaluator 的判定有争议，不硬修，在报告里标【争议】，停下施工等调用方裁决。

这防止了一种特定的死循环：coder 明明觉得自己是对的，但为了"让 evaluator 满意"而反复修——越修越偏离原本正确的实现。

## 保留施工尝试轨迹

打回循环里最容易流失的信息是**失败的尝试本身**。

每一轮 coder 是独立会话——第 2 轮启动时，上一轮的"我试过了这条路"不在它的上下文里。如果不显式记录，一个子任务可能反复尝试同一条注定失败的路径，agent 和人类都看不出来"已经重复撞墙两次了"。

解法不是给 coder 塞更长的上下文，而是在 plan 文件里加一段**施工尝试记录**，由调度者在每轮结束后追加：

```
## 施工尝试记录

### 第 1 轮（失败）
- 尝试方向：{coder 本轮的核心实现思路}
- 打回原因：{evaluator 指出的未达标项}
- 可复用产出：{本轮里仍然有效的部分，如已加好的索引}

### 第 2 轮（失败）
- 尝试方向：...
- ...
```

这段**不是 coder 写**，也**不是 evaluator 写**——由调度者从双方报告里抽取。调度者在 spawn 下一轮 coder 时，把这段作为 prompt 的一部分显式传入。

### 这段带来的好处

- **新一轮 coder 知道坑在哪**：不会再次尝试已被证伪的方向，节省一次循环
- **升级到人类时有完整轨迹**：人类拿到的不是"打回三次"这个事实，是"三次尝试分别是什么、分别栽在哪"
- **task-designer 能看清契约是否需要修**：连续几轮卡在同一条验收项上，往往意味着这条验收条目本身有问题
- **知识沉淀**：这段记录在任务结束后应该由 dreamer 审视——反复失败的共同原因往往是值得上浮的踩坑经验

### 不越界

施工尝试记录里**不写**：

- coder 的情绪或自辩
- evaluator 的主观评价
- 任何"本来应该怎么样"的后验判断

只记**事实**：尝试了什么方向、什么条目未达标、是否留下可复用产出。

## 升级后怎么办

当 evaluator 判定 🛑 调用方裁决时，通常有四种处理路径：

### 路径 1：契约修订

如果是契约本身的问题，调用方把问题转给 task-designer，task-designer 修契约，然后重新 spawn coder 和 evaluator 走流程。

### 路径 2：人类介入施工

某些复杂问题（如环境配置、工具链问题）用 agent 解决不了，人类直接改。改完在任务 memory 里记一条"本子任务由人类收尾，原因：...",保留痕迹。

### 路径 3：降级验收标准

某些验收标准可能过严（例如"覆盖率必须 100%"），人类判断后降级为"覆盖率 80%"并更新契约，重新走流程。

### 路径 4：放弃子任务

极少数情况——这个子任务本身不应该做。人类决定回退、改方案、或者放弃。

这四种路径的共同点：**人类在里面**。升级机制不是要替人类做决定，是要**明确"到了人类该做决定的时刻"**。

## 成本分析

有人会算账：3 轮复跑，意味着每个子任务可能跑到 6 次测试（coder 自验 3 次 + evaluator 复跑 3 次）。是不是太贵？

短算：

- 单次测试跑 1 分钟
- 一个子任务平均 1.5 轮达标
- 成本 = 2 × 1.5 × 1 = 3 分钟

即使走到 3 轮极限，成本也就 6 分钟。

长算：

- 省掉的成本是**漂移交付物的修复成本**——一个通过自报"测试通过"混过去的 bug，线上发现后的修复成本可能是 6 分钟的 1000 倍
- 3 轮升级到人类后，人类的判断**同时修了契约 / 代码 / 流程**三件事，不是只修一个 bug

这笔账是划算的。**验收复跑的成本是线性的，自报漂移的成本是指数的**。

## 对使用者的操作建议

- **必须让调度层维护轮次**。不要让 evaluator 自己数——它数不准。
- **复跑成本真的高时**（比如 E2E 测试），允许接受证据，但要求证据里包含 **运行时间戳 + 完整输出 + 环境信息**三件事。
- **争议和打回分开走**。调度层识别 evaluator 输出里的"契约问题"标记，判断走哪条路。
- **升级不是失败**。到 3 轮升级是设计预期，不是系统异常。调用方收到升级时不要"再试一次"——那就绕过了机制。
