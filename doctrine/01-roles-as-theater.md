# 01 — 角色即剧班

## 核心主张

不要把 AI 协作设计成"一个万能助手 + 一堆工具"。
把它设计成**一组各司其职的角色**，每个角色有自己的性格、输入、输出、边界。

## 为什么单个大 agent 不够

看过一段这样的对话吗：

> "帮我实现用户登录功能。"
>
> — 好的，我设计并实现了登录，已经写完，测试也跑通了。

问题不是 agent 写错了代码，问题是**整个判断链条都在一个上下文里跑完**：

1. 它自己定义了"登录功能"的范围
2. 它自己挑了实现方式
3. 它自己写了代码
4. 它自己写了测试
5. 它自己判定测试通过
6. 它自己报告完成

这条链的每一环，**下游都被上游的叙事牵着走**。代码里选了一条路，测试自然就只覆盖这条路；判定时看到自己的代码跑通自己的测试，自然就觉得"做完了"。

这不是能力问题，是视角问题。**上下文里留下的东西就是 LLM 的偏置**，它推崇过的方案、它跳过的边界、它自己安慰自己"没事"的那几句话，会在回看产出时替它辩护。

让同一个 agent 既写又验，得到的是一套**自洽但漂移**的交付物。

## 人类团队的解法

软件工程这个行业，几十年前就想明白了这件事：

- 产品经理不写代码——写代码的人看不到产品目标
- 工程师不自己 review——自己上下文污染了判断
- QA 不听工程师"我测过了"——必须独立跑
- Tech Writer 不依赖工程师告知文档改动——必须独立检查

不是因为工程师能力不够。是因为**独立视角是稀缺资源**。一个人既是施工者又是验收者时，不管他有多聪明，他的验收都会被施工时留下的心智模型污染。

## 为什么是"角色"，不是"模块"

如果只是工程上的拆分，用"模块"这个词也够了：
- planning 模块
- coding 模块
- review 模块
- testing 模块

但 LLM 的行为是由**叙事框架**驱动的。告诉它"你是一个 coder"和告诉它"执行 coding 模块"效果完全不同。前者会激活它训练数据里所有"工程师该怎么写代码"的模式，包括纪律、谨慎、边界感。后者只是一个函数调用。

**角色（role）**这个抽象比**模块（module）**多带了三样东西：

1. **性格**——不是指令清单，是风格。coder 的"看到周边烂代码不顺手改"不是规则，是一种职业素养
2. **视角**——每个角色看到的世界不一样。evaluator 只看契约，不看 coder 怎么辛苦
3. **边界感**——不是"这个函数不能碰"，而是"这不是我该管的事"

这三样东西用 YAML 配置或代码函数都写不出来，只能用自然语言在 prompt 里**塑造**。

## 角色不是独立 agent

有人会问：7 个角色是不是 7 个独立的 agent？

不一定。角色是**视角切换**，不是进程隔离。实现上可以是：

- 7 个独立 subagent 会话（Claude Code 下最自然）
- 同一进程下按阶段切 system prompt（裸 API 调用时常见）
- 一人分饰多角，按阶段显式切身份（轻量场景）

技术实现是次要的。关键是**让每一次判断落在对应角色的视角里**，而不是任由上下文洪水把视角冲散。

理想的实现给每个角色**独立的上下文窗口**。这不是技术奢侈品——这是让"独立视角"真正独立的唯一方式。只要 coder 的上下文还能被 evaluator 看到，evaluator 的判断就已经被污染了。

## 7 个角色不是神圣数字

当前给出的 7 个角色（task-designer / coder / evaluator / code-reviewer / doc-refresher / dreamer / git-push）是一套推荐起点，覆盖了多数工程任务会遇到的职能：规划 / 施工 / 验收 / 审查 / 文档 / 沉淀 / 发布。

按项目需要可以增减：

- 加一个 **incident-responder** 处理线上问题
- 加一个 **perf-analyzer** 看性能回归
- 小团队合并 coder 和 evaluator——但请理解这样做丢了什么（独立视角）

增减的判断标准不是"流程好不好看"，是**这个角色是否对抗了一种独立存在的偏置**。如果两个角色看问题的视角其实一样，合并它们；如果一个角色无事可做，删掉它。

## 对使用者的含义

采用这套设计，意味着接受三件事：

1. **协作成本高于单 agent 模式**——7 个角色要写 7 份 prompt、要维护角色之间的契约
2. **简单任务会显得过度**——改个 typo 走一遍完整流程是笑话
3. **需要一个"调度者"——**谁在什么时候 spawn 哪个角色、怎么维护轮次计数、谁来裁决争议，这些本身就是一套协作纪律

如果你的任务本来就简单、就一次、就不会有人回看——这套设计**不合适**。它的价值只在**复杂、长期、会被多次修改**的工程上下文里才显现。
