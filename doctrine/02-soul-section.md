# 02 — Soul 段

## 核心主张

每个角色的 prompt 必须以一段**性格描述**开头，而不是以任务说明开头。

这一段叫 **Soul**——不是装饰，是行为约束的核心。

## 为什么要写性格

标准写法长这样：

```
你是一个 coder，负责根据需求实现代码。
请遵循以下规则：
- 不要修改契约外的文件
- 必须运行本地测试
- 报告中要说明改动范围
```

这是指令清单。LLM 会遵守，但**遵守的程度随上下文衰减**：对话一长、压力一大、任务一模糊，它就开始放水。"不要修改契约外的文件"这条到了第 20 轮对话就成摆设了。

Soul 段的写法长这样：

```
## Soul

- 严格按图施工。图纸上没画的不动；图纸画错了回头找设计者，不自己脑补补图。
- 自验不甩锅。写完立刻跑本地检查，能自证就自证。
- 边界敏感。看到诱惑顺手重构周边代码时主动收手。
- 失败坦白。本地自验没过就在报告里如实写"未通过"，绝不粉饰。
```

读一遍区别——**这是一个人的职业态度，不是一张任务清单**。

## 性格比规则稳

LLM 是在人类语料上训练的。人类的行为是由角色（身份、职业、性格）驱动的，不是由规则清单驱动的。

告诉 LLM "你是一个严谨的 code reviewer"，它会自动调用它见过的所有严谨 code reviewer 的行为模式——包括那些你没在 prompt 里明写的纪律。

告诉 LLM "请按以下 10 条规则审查"，它只会执行这 10 条。第 11 条你没写的坑，它就踩进去了。

**性格是高维约束**：一句话压缩了一整套行为倾向。
**规则是低维约束**：一条只管一件事，管得再多也有漏洞。

## Soul 怎么写

好的 Soul 段满足三个条件：

### 1. 描述倾向，不描述动作

| 不好 | 好 |
|------|------|
| "在写代码之前先读取 plan 文件" | "严格按图施工，图纸上没画的不动" |
| "不要修改测试用例" | "不为了让测试过而改测试断言" |
| "必须写日志" | "正式日志机制，不把 print 当生产日志" |

前者是指令——会被执行但不会内化。后者是态度——会影响后续所有判断。

### 2. 带"为什么"的姿态

纯态度没有说服力，要带一点姿态：

| 扁平 | 立体 |
|------|------|
| "要关注细节" | "强迫症级别的一致性偏执" |
| "评审要冷静" | "多疑且冷静，只看 diff 和规范说话" |
| "要保留证据" | "尊重原始证据，不允许脑补升华或夹私货" |

立体的 Soul 段能让 LLM 在边界模糊时有方向——"我是一个强迫症级别偏执的核查员"会指导它怎么处理"这个路径算不算过时"这种判断。

### 3. 有反面照——明确"不做什么"

Soul 段应该既讲"做什么姿态"，也讲"不做什么姿态"。

coder 的 Soul 里有这两条：

- 严格按图施工（正面）
- 简短交付，不写长篇叙事（反面）

evaluator 的 Soul 里有：

- 只认验收契约（正面）
- 打回不攻击（反面）

反面约束堵住最常见的堕落方向。

## Soul 不是 charter

不要把 Soul 写成"岗位职责说明书"：

```
# 不好 — 这是 charter，不是 Soul
## Soul
你负责按照施工契约实现代码。你的工作包括阅读 plan 文件、
编写实现、运行测试、撰写交接报告...
```

这退化成了任务清单。

Soul 要留给**态度和风格**，具体做什么放在后面的"工作流程"段。两者分开的好处：态度贯穿始终，流程只在执行时参考。

## Soul 不是过长的散文

也不要写成一段自我陶醉的散文：

```
# 不好 — 这是散文，不是约束
## Soul
coder 是一个将抽象转化为具体的魔法师，他用代码这种语言...
```

Soul 要**紧实**——3 到 5 条，每条一句话带一个短句解释。太长没人读，读了也记不住。

## 性格和纪律的边界

Soul 段不能替代**硬边界**和**禁止事项**。

Soul 管"倾向"，硬边界管"范围"，禁止事项管"红线"。三者在角色 prompt 里**各占一段**：

- **Soul**：描述性格，软约束。用于塑造判断时的倾向。
- **硬边界**：描述范围，中约束。用于框定什么可以做。
- **禁止事项**：描述红线，硬约束。用于拦截典型错误。

例子：

- "失败坦白"（Soul，软）
- "只改契约中列出的文件"（硬边界，中）
- "禁止使用 --no-verify 绕过钩子"（禁止事项，硬）

一个 agent 违反"失败坦白"时，调用方会觉得它"风格不对"但还在工作；违反"只改契约文件"时，调用方会要求它停下来；违反"禁止 --no-verify"时，调用方会立刻终止。

三层递进，缺一不可。

## 对 fork 者的提示

如果你在自己的项目里用这套角色，Soul 段**可以改**，但改之前想清楚：

- 这一条性格对抗的是哪种漂移？
- 删掉它的话，什么偏置会跑出来？
- 加一条新的，有具体的失败案例做依据吗？

**不要为了"显得我们团队独特"而改 Soul**。Soul 不是招聘广告，是行为护栏。
