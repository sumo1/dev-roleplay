# 05 — 三层记忆

## 核心主张

Agent 协作会产生大量"决策备忘"、"踩坑笔记"、"推翻前提"的信息。这些信息应该分**三层**存放：

1. **按日沉淀层**（daily memory）——随做随记的流水账
2. **任务汇总层**（task SUMMARY）——任务结束时按主题聚类的汇总
3. **跨任务知识层**（knowledge）——上浮到项目级的普适原则

**写入、整理、上浮由不同角色负责**，不让一个 agent 既当运动员又当裁判员。

## 为什么要分层

常见做法是把所有"决策和教训"堆在一个地方：

- 放一个 `DECISIONS.md` 里——越长越乱
- 放在 commit message 里——搜不到、看不见
- 让 agent 自己"总结一下最近学到的东西"——通常是幻觉升华

这些做法都有同一个问题：**记录、提炼、沉淀是三种完全不同的任务**，混在一起必然乱。

三层记忆的好处是：

- **每一层有明确的职责**：记什么、不记什么一清二楚
- **每一层有明确的写入角色**：知道谁来写、谁能改
- **每一层有明确的保留期**：短期的归短期处理，长期的按长期维护

## 第一层：按日沉淀

位置：`docs/task/{task-id}/memory/YYYY-MM-DD-{topic}.md`

**写入角色**：任务执行过程中的所有 agent 和人类。coder 发现了契约的漏洞、evaluator 发现了某条规则的灰色地带、task-designer 推翻了之前的判断——都写在这里。

**写入规则**：

- 一条一个文件，不合并
- 文件名带日期，方便按时间线追溯
- 内容简短：背景、结论、证据链
- 不追求美观，追求**及时**

**不写入什么**：

- 纯情绪（"今天很痛苦"）
- 纯事实（"今天改了 3 个文件"——git log 里有）
- 已经在工程规范里写过的东西

## 第二层：任务汇总

位置：`docs/task/{task-id}/memory/SUMMARY.md`

**整理角色**：`dreamer`。

**触发时机**：

- 任务阶段完成
- 按日条目达到一定数量（例如 10 条以上）
- 距上次整理时间较长
- 调用方显式要求

**整理动作**：

- 按**主题**聚类（不按日期）
- 每主题保留核心结论、关键证据、被否决的方案、相关提交
- 原始按日条目**保留不动**——SUMMARY 只做索引 + 提炼

**为什么不让 coder 或 task-designer 自己写汇总**：

- coder 的视角还沉在"当下的实现"，写汇总会带偏见
- task-designer 的视角在"整个任务"，写汇总会升华过度
- dreamer 的视角是**冷静的收纳者**，唯一关心的是"哪些条目值得留、怎么分类"

## 第三层：跨任务知识

位置：`docs/knowledge/{category}/{topic}.md`

**上浮角色**：`dreamer`，但必须经**调用方确认**后才真正写入。

**上浮的硬标准**（同时满足才上浮）：

- 去掉任务专名后，结论**仍然成立**且**仍有信息量**
- `docs/knowledge/` 或 `docs/engineering/` 里**尚未覆盖**同样的原则
- 来源有**具体证据**（被推翻的假设、踩过的坑、讨论记录），不是空泛口号

只满足"听起来很对"但无证据的条目，**不上浮**。

**知识分类（典型）**：

- `background/` — 项目 / 产品背景、生态定位
- `principles/` — 工程元原则（怎么判断、怎么决策）
- `ecosystem/` — 外部系统 / 依赖的领域知识
- `pitfalls/` — 反模式 / 踩坑清单

**上浮时必须**：

- 脱敏——去掉任务专属代号
- 加引用——在 knowledge 条目末尾注明来源 task memory
- 双向链接——原 task memory 条目头部加一行指向 knowledge 新条目

## 为什么上浮要经调用方确认

dreamer 有能力判断"这条值得上浮"，但没有权力独自决定——因为 knowledge 层是**项目级资产**，误上浮比不上浮代价大：

- 误上浮了错误原则：全项目开始跟着错
- 误上浮了重复条目：knowledge 开始膨胀，索引失效
- 误上浮了未定型结论：后续打脸时回退成本高

调用方在这里是**守门人**，不是决策者——dreamer 提出的候选大多会被接受，但守门这一步本身就提供了一道风险过滤。

## 不让 agent 自己管自己的记忆

这是三层记忆最重要的设计原则：

> 写入 memory 的 agent，不负责整理 memory。
> 整理 memory 的 dreamer，不负责上浮到 knowledge（上浮需调用方确认）。
> 上浮到 knowledge 后，dreamer 不能再修改 knowledge 的核心结论（那是项目级资产）。

这个原则解决了单 agent 记忆管理的两个失败模式：

### 失败模式 1：自我辩护

让 coder 管理自己的 memory，它会倾向于保留**证明自己正确的条目**，丢掉**暴露自己错误的条目**。随着时间推移，memory 变成一篇自传，不是事实档案。

### 失败模式 2：过度升华

让任何 agent 自己"总结一下"，它会不自觉地把具体的一次教训**升华为普适原则**。一次踩坑被包装成"本项目的 X 原则"，但其实没有足够证据支撑。

让 dreamer 独立负责整理 + 提出上浮候选，两个失败模式都被堵住：

- dreamer 不写入 memory，没有自辩冲动
- dreamer 上浮需要调用方确认，无法独断升华

## 三层之间的流动

```
按日沉淀   →  任务汇总  →  跨任务知识
 (daily)      (SUMMARY)      (knowledge)
```

- **daily → SUMMARY**：由 dreamer 蒸馏，原件保留
- **SUMMARY → knowledge**：由 dreamer 提出候选，调用方确认后上浮
- **knowledge → 项目级规范** (docs/engineering/)：由人类决定

反向流动**通常不发生**：

- knowledge 不会被降级回 SUMMARY
- SUMMARY 不会被降级回 daily

但**例外**是：某条知识被证伪后，可以**归档**到 archive 目录并在原位置留一个"已归档"标记。归档不是删除——保留审计价值。

## 冲突处理

两条 memory 说法相反时，dreamer 的规则是：

> **不下结论**。标记为 ⚠️ 冲突，交给调用方判定。

这和"打回循环"里的争议处理是同一套哲学——**agent 层不做有争议的元决策，暴露冲突让人类判**。

## 对使用者的操作建议

- **daily 写入要及时**：发生的当下写，不然细节会丢失
- **SUMMARY 整理要有节奏**：不要等到几十条才整理，通常 10 条是合适阈值
- **knowledge 上浮要有敬畏**：每条都是长期负债（需要维护 / 更新 / 重读），轻易不加
- **归档不删除**：哪怕某条知识错了，归档比删除更尊重历史
- **双向链接是必须的**：上浮后 daily 条目要加链接，不然原始证据和升华结论断了联系

## 记忆不是 log

最后澄清一个容易混的概念：

**三层记忆 ≠ 操作日志**。

记忆记录的是**决策和教训**——"我们为什么这么选"、"我们踩过什么坑"。
操作日志记录的是**事实**——"什么时候跑了什么命令"、"改了哪些文件"。

前者由 agent 主动写（因为只有参与决策的 agent 知道为什么）。
后者由工具自动记（git log、CI log、监控日志）。

两者**都不能替代对方**。记忆里不要写"我今天改了 3 个文件"——那是 log 的事。Log 里也不会写"我们为什么放弃了方案 B"——那是记忆的事。

把 log 的事写进记忆，记忆会被噪音淹死。把记忆的事留在脑子里，三个月后就全部蒸发了。
