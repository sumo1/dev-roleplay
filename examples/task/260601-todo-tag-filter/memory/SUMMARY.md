## 主题 1：tag 字段索引选型

**核心结论**：用 GIN 数组索引，不用全文索引（tsvector）。

**关键证据**：

- 数据库原生支持数组 `@>`（包含）操作，查询语义清晰
- 全文索引需触发器或 generated column，复杂度高一倍
- 现有数据量（百万级以内）GIN 数组索引足够

**被否决的方案**：

- 全文索引（GIN + tsvector）—— 详见归档 [`archive/2026-06-01-considered-fulltext-search.md`](./archive/2026-06-01-considered-fulltext-search.md)
- 普通 B-tree 索引——无法直接支持数组包含查询

**原始条目**：[`2026-06-01-tag-index-decision.md`](./2026-06-01-tag-index-decision.md)

## 主题 2：HTTP 语义——空结果不是 404

**核心结论**：列表查询找不到匹配项返回 HTTP 200 + `data: []`，不返回 404。

**关键证据**：

- 404 表达"URL 指向的资源不存在"——列表集合永远存在
- 调用方一次 `if (data.length === 0)` 即可处理；用 404 会污染错误处理
- HTTP RFC 9110 § 15.5.5 支持

**被否决的方案**：

- HTTP 404 + 业务错误码：增加调用方区分负担
- HTTP 204 No Content：与项目"成功永远返回 `{ code: 0, data: ... }`"约定不一致

**原始条目**：[`2026-06-02-empty-result-not-404.md`](./2026-06-02-empty-result-not-404.md)

**🚀 已上浮**：[`docs/knowledge/principles/empty-result-vs-404.md`](../../../knowledge/principles/empty-result-vs-404.md) — 该判断不依赖本任务上下文，未来任何"集合查询无匹配"的场景都适用。

## 主题 3：tag 参数校验严格度

**核心结论**：正则 `^[a-zA-Z0-9_-]{1,50}$`——大小写 + 数字 + `-` + `_`，长度 1-50。

**关键证据**：

- 现有数据库 tag 抽样里同时存在大小写——更严格的纯小写正则会排除合法数据
- 长度 50 与现有最长记录（30）有冗余但不夸张

**被否决的方案**：

- 严格版 `^[a-z0-9-]{1,30}$`——破坏现有数据兼容性
- URL-safe 任意字符——开放注入面 + GIN 索引性能下降

**原始条目**：[`2026-06-02-tag-validation-regex.md`](./2026-06-02-tag-validation-regex.md)

## 主题 4：分页选 cursor (created_at) 不选 offset

**核心结论**：cursor 分页用 `created_at` 作为游标。

**关键证据**：

- offset 在持续写入时翻页会漏 / 重——cursor 不会
- 不需要额外索引——主键 ULID 时间有序天然覆盖
- `created_at` 比 `id` 对调用方更自解释

**被否决的方案**：

- offset 分页——翻页一致性问题
- cursor 用 `id`——技术上等价，但调用方需要懂 ULID 内部时间编码

**已知遗留风险**：相同毫秒时间戳的两条记录跨页可能重复 / 漏。当前数据量不触发，未来加 `(created_at, id)` 二级排序。

**原始条目**：[`2026-06-03-cursor-vs-offset-pagination.md`](./2026-06-03-cursor-vs-offset-pagination.md)
