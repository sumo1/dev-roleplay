# 06 — 反模式

## 核心主张

这套框架**不是万能的**。有些任务用它反而更慢、更笨。

这一篇讲清楚边界：什么场景**不该**套 dev-roleplay-harness。

认识反模式和认识正模式同样重要——没有反模式的框架是宗教，不是工程方法。

## 反模式 1：一次性小改

**场景**：改一行 typo、调一个变量名、换一个颜色值。

**为什么不适用**：

整套流程的开销（规划 → 契约 → 施工 → 验收 → 审查 → 文档核查 → 提交）本身有固定成本。一次性小改的**内容成本**远小于**流程成本**——套流程是浪费。

**替代做法**：

- 人类直接改
- 或者单 agent 直接改
- 不需要 plan 文件、不需要双契约、不需要三轮验收

**如何识别**：

- 改动能在一分钟内写完
- 不涉及契约、schema、对外接口
- 不需要测试验证（视觉效果、字符串修正等）

**边界提示**：

"一行改动"不一定都是一次性小改。比如改一个 API 的默认行为——看似一行，实际是破坏性变更，必须走完整流程。判断标准是**影响面**，不是**代码行数**。

## 反模式 2：探索性 prototyping

**场景**：试一个新想法、跑一个 POC、看看某个 API 能不能用。

**为什么不适用**：

探索的核心价值是**快速试错**。本次试错的产出大概率会被扔掉。套一个"施工契约→验收契约→复跑"的流程等于给一次性代码盖一座豪宅。

更重要的是：**探索阶段的价值不在"产物正确"，而在"获得信息"**。验收标准应该是"我学到了什么"，不是"代码测试全部通过"——前者无法用双契约表达。

**替代做法**：

- 直接让 agent 自由发挥
- 或者用更轻量的流程（例如只用 coder 角色，不走后续验收）
- 探索完成后，如果决定"认真做"，再启动完整流程重写

**如何识别**：

- 目标是"验证某个想法是否可行"，不是"交付一个功能"
- 产物大概率会被重写或丢弃
- 没有真实用户会受影响

**边界提示**：

"探索"和"探索后的正式实现"是两个阶段，**不要混**。探索阶段可以粗放，但进入正式阶段后必须重新走完整流程——不要把探索代码直接当成正式代码合并。

## 反模式 3：单文件脚本

**场景**：写一个一次性的数据处理脚本、一个简单的爬虫、一个本地工具。

**为什么不适用**：

单文件脚本往往：

- 没有模块划分（整个代码在一个文件里）
- 没有对外契约（自己用自己）
- 没有长期维护（跑完就删）

双契约需要"施工契约"和"验收契约"配对，但脚本的"契约"往往就是"跑出来结果是对的"——无法机器判定，也没必要机器判定。

**替代做法**：

- 人类写 + 人类验（本来就是给自己用的）
- 或者单 agent 写 + 人类看一眼输出

**如何识别**：

- 不会被别人用
- 不会被 CI / 生产环境依赖
- 写完跑一次就完事

**边界提示**：

一个脚本如果**重复运行**（例如每天跑一次的定时任务）、或者**被团队共享**（放在团队工具仓库里），它就不再是反模式——那是一个服务，走完整流程。

## 反模式 4：高度依赖人类判断的任务

**场景**：UI 设计决策、文案语气调整、图标选择、设计系统一致性。

**为什么不适用**：

这类任务的"验收标准"依赖**人类审美 / 直觉 / 品味**。验收契约要求"可机器判定"，但审美无法机器判定。

硬套流程的结果是：

- 验收契约写得像"元素居中对齐"——表面达标但真实美感完全不对
- 或者验收契约写成"由 Lead Designer 审核通过"——退化成"人类说了算"，整个自动化流程失去意义

**替代做法**：

- 人类全程参与
- Agent 辅助生成候选，人类决策
- 走设计评审流程而不是工程验收流程

**如何识别**：

- 判断标准含"好看"、"合适"、"品牌感"这类主观词
- 两种实现在机器眼里都达标，但人眼看差异明显
- 最终需要人类拍板

**边界提示**：

如果一个任务**大部分**是工程问题、**小部分**是审美问题，可以走工程流程完成 80%，最后留一个"人类审美 review"的人工关卡。不要为了上框架而把审美问题机器化。

## 反模式 5：时间紧迫的线上事故

**场景**：生产环境挂了、用户投诉爆炸、P0 级 incident。

**为什么不适用**：

完整流程的价值是**保证质量**，代价是**时间**。线上事故的优先级是**先止血后追根**——等你走完 task-designer → 双契约 → evaluator 复跑 → code-reviewer 审查，用户已经跑光了。

**替代做法**：

- 直接修（人类决策 + agent 辅助 / 或人类亲手）
- 事故缓解后补完整流程（回填 plan 文件、加测试、做根因分析）
- 事故的教训通过 memory 机制沉淀

**如何识别**：

- 有明确的时间压力（"5 分钟内必须恢复"）
- 业务影响大于工程完美度
- 决策层愿意接受"先粗后细"

**边界提示**：

事故止血**之后**必须补流程。事故期间可以"跳过"，但事后回填——plan 文件、验收标准、post-mortem 都要补上。不补的话，同样的事故会再发生。

## 反模式 6：不需要沉淀的临时项目

**场景**：为某个会议准备 demo、临时做的竞品分析、一次性 workshop 材料。

**为什么不适用**：

dev-roleplay-harness 的很多价值在于**长期沉淀**：

- plan 文件给未来的人看
- memory 给未来的自己看
- knowledge 给整个项目看

如果这个任务本身是**一次性的**、**不会被回看的**、**不需要沉淀的**——三层记忆白写了，双契约白写了，连 code-reviewer 的审查报告都没人看。

**替代做法**：

- 轻量 agent 协作
- 或者人类直接上手
- 省掉所有文档生成

**如何识别**：

- 项目明确有"结束日期"
- 产物不会进入任何长期仓库
- 没有未来的使用者

**边界提示**：

有些项目**看起来**一次性，**实际上**会被引用。例如一份"临时"调研报告，半年后有人回来翻。这种情况下"轻度沉淀"比"完全不沉淀"好——可以只做 memory 记录，跳过完整流程。

## 共同特征

把上面 6 个反模式对照看，会发现它们有共同特征：

- **成本不对称**：流程成本高于任务本身成本
- **验收无法机器化**：审美 / 探索 / 脚本往往无法用可机读契约表达
- **时间维度错配**：一次性 vs 长期、紧急 vs 从容
- **受众错配**：给自己 vs 给团队 vs 给项目

识别反模式的核心问题是：

> **这个任务，三个月后还有人会读它、改它、参考它吗？**

如果答案是"不会"——大概率是反模式。
如果答案是"会"——大概率值得走完整流程。

## 不要机械套用

也不要反过来机械套用反模式。**反模式不是拒绝的借口**。

一个常见的退化：

> "这是一次性脚本，不用走流程。"
>
> 结果三个月后，这个"一次性脚本"被 CI 依赖了、被 5 个人修改过了、但没有任何测试和文档。

判断是否是反模式的时机不是**最终形态**，是**当前形态**。如果一个脚本**现在**就要被 CI 依赖——它从第一天起就不是反模式。

判断错误的代价是非对称的：

- 把非反模式误判为反模式：长期债务
- 把反模式误判为非反模式：短期时间浪费

**宁可多走一点流程，也不要少走一点纪律**。走流程是显性的，省流程是隐性的。

## 对使用者的操作建议

在每个任务开始前，先问自己：

1. 这个任务三个月后会被回看吗？
2. 验收标准能否机器化？
3. 任务成本是否大于流程成本？
4. 是否存在真实的多人协作 / 多 agent 协作需要？

四条里只要有一条是否定的，就考虑**降级流程**：

- 去掉 `task-reviewer`（无专项审查需要）
- 合并 coder 和 evaluator（单人场景）
- 不建 `memory/` 目录（无沉淀需要）
- 不走 doc-refresher（无文档依赖）

四条都是否定的，那就**别用 dev-roleplay-harness**——人类或单 agent 直接做完就行。

识别自己不适用的场景，是对使用者最大的尊重。
