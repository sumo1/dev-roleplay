# 多标签 AND/OR 过滤推迟到下一任务

> 日期：2026-06-03
> 作者：task-designer

## 背景

实现 step1 后被问到："要不要顺手支持 `?tag=a,b&match=all`？"

## 决策

**本任务不做。** 留给独立的下一任务。

## 理由

- 单标签过滤已经覆盖当前已知用户场景的 95%（产品确认）
- 多标签过滤需要重新设计 query 参数 schema（`tag` vs `tags[]`、`match` 模式枚举）
- GIN 索引对多值过滤的性能特征不同——`tags @> ARRAY['a','b']`（AND）和 `tags && ARRAY['a','b']`（OR）需要分别 benchmark
- 当前这个 PR 范围已经在三个文件层（http / service / repo）+ migration——继续叠加会让 review 难度倍增

## 被否决的方案

- **本任务一并做**：契约从"单值"扩到"多值 + 操作符"是个二阶变化，不该混在 step1 里
- **预留接口但不实现**：契约里写 `tags?: string[]` 但 handler 只取首个——制造误导

## 证据

- 产品确认当前 UI 上没有"多选标签"的入口——多标签过滤是技术驱动而非产品驱动
- step1 PR diff 已经 +180/-12，再加多标签会双倍
